# Astravar 2.3.2 optional Pushy wake protocol

Cloudflare remains the synchronization authority. Pushy is disabled unless the existing owner-private Worker has `PUSHY_API_KEY` and `ASTRAVAR_PUSH_KEY_B64` configured privately. Missing push configuration does not affect campaign reads, durable command submission, authenticated Android fetch, Room commits, or immutable receipts. No Firebase service account, OAuth exchange, project configuration or Android key is needed. Existing Google/Firebase resources are not deleted or changed by this replacement.

`POST /v2/campaigns/{campaignId}/push-token` accepts only `{provider: "pushy", token, notificationsEnabled}` from the currently paired authenticated device with its existing campaign grant. Missing or other provider values are rejected. DELETE removes that device registration even if the optional sender is unconfigured. Tokens are encrypted with AES-GCM using owner/campaign/credential identity and the explicit Pushy provider as authenticated additional data. The encrypted envelope also binds `provider: "pushy"`. Existing encrypted legacy provider tokens are never transmitted to Pushy; only an explicit authenticated Pushy registration replaces them. No destructive D1 migration is used. Credential/grant revocation or deletion still removes registrations through existing migration0004 triggers. Rotation and stale-recipient cleanup compare token hashes to preserve concurrent registration changes.

Pushy DATA contains exactly `type`, `version`, `issuedAt`, `expiresAt`, `wakeId`, and `signature`, all strings. Type is `ASTRAVAR_CAMPAIGN_SYNC_WAKE`, version is `2`. Expiry is the earliest of issuedAt+30000 milliseconds, grant expiry, and device credential expiry. No campaign, grant, credential, command, character, source text, notification text, or gameplay value is sent in the wake payload.

The signature is unpadded base64url HMAC-SHA256. Its key is the UTF-8 lowercase hexadecimal SHA256 of the existing device secret. The signed bytes are UTF-8 newline-separated values in this exact order: type, version, issuedAt, expiresAt, wakeId. Android verifies its local paired credential, expiry, signature in constant time and wake replay identity, then fetches typed commands independently through its authenticated client. Current grants, revisions and atomic authorization remain enforced by that separate protocol. A wake never authorizes or executes gameplay.

The sender uses only the documented fixed HTTPS API `https://api.pushy.me/push`, authenticating with the backend-only API key query parameter. Redirects are rejected. JSON is `{to: <registered token>, data: <signed wake>, time_to_live: 30, collapse_key: "astravar-wake"}`. Requests time out after at most eight seconds by default and are dispatched using Worker `waitUntil`, outside the command response. Provider failures never roll back or remove queued commands. Generic HTTP/API failures retain registrations; an explicit failed token in a valid success response removes only the matching stale token hash. No raw provider errors or request URLs are logged.

Pushy's [official send API](https://pushy.me/docs/api/send-notifications) defines the token, payload, TTL and collapse behavior. [Official Android integration](https://pushy.me/docs/additional-platforms/android) and [pricing](https://pushy.me/pricing) must be checked for current setup and free-tier limits. SDK installation and API acceptance do not establish physical-device delivery. The Android integration is opt-in; it does not require exact alarms, battery-optimization exemptions or a permanent foreground service. Android Doze, app standby, OEM battery rules, force-stop and network loss may delay or prevent delivery. Foreground, manual Sync Now and existing battery-conscious scheduled recovery remain operational without Pushy. Instantaneous screen-off delivery is not guaranteed.

Set owner-private `ASTRAVAR_SYNC_METRICS=1` to emit request_received/request_completed, queue_accepted, push_requested and push_accepted_by_pushy/push_failed events. Timings contain random correlation IDs, route category, status and duration; they omit API keys, tokens, campaign IDs, character data and source text. A Pushy acceptance metric proves provider acceptance only. Android arrival, WorkManager start, Room commit, immutable receipt and independent saved-revision readback require separate evidence before reporting end-to-end latency. Unit/fixture results do not establish Galaxy S26 screen-off, Doze or battery-restriction acceptance.

## Lean read selectors

`get_inventory` and `get_equipment` retain their existing unfiltered calls and accept optional `holderProfileId`. `INVENTORY_BY_HOLDER_V1` joins only explicit committed item-placement relations to original items/details/properties, under the same owner/campaign/grant. It never infers assignments from owner display names or invents placements. Missing holder identities return no matches; lack of inventory scope is denied. Migration0006 adds expression indexes for holder, property item and companion resource identity lookups. Tests inspect SQLite query plans to verify both holder and property indexes are used.

`get_character_resources` now returns `RESOURCE_COUNTERS_V1`: only saved resource counters from the selected profile's sheet and its companion counters, with revision, source, freshness and explicit null remaining values. Unrelated capability/spell/research text is omitted. Existing get_character_hp and get_character_abilities remain narrow, scoped selectors. Resource reads use one grant lookup plus one bounded indexed data query; pagination applies each cursor before each branch limit.

All multi-kind reads compare cursor kind and recordId as separate keys. The inherited kind+separator comparison could skip or repeat rows when kinds shared prefixes such as item and item-details; composite comparisons fix that while retaining the existing opaque cursor format.
