# Astravar 2.3 push wake protocol and verification boundary

Push is optional and disabled unless the existing owner-private Worker has `FCM_PROJECT_ID`, `FCM_SERVICE_ACCOUNT_JSON`, and `ASTRAVAR_PUSH_KEY_B64` configured privately. No service-account key, owner release key, device credential, or registration token belongs in source control. Installing a receiver or issuing a queue response does not prove physical-device delivery.

`POST /v2/campaigns/{campaignId}/push-token` accepts only `{token, notificationsEnabled}` from the currently paired authenticated device with its existing campaign grant. DELETE removes that device registration. AES-256-GCM encrypts each registration with owner/campaign/credential identity as authenticated additional data. Credential/grant revocation or deletion removes its registration through migration0004 triggers. An FCM UNREGISTERED response deletes only the matching stale token hash, preserving a concurrently rotated registration. Other send failures preserve the queue and token.

FCM DATA contains exactly `type`, `version`, `campaignId`, `credentialId`, `grantId`, `grantRevision`, `issuedAt`, `expiresAt`, `wakeId`, and `signature`. All values are strings. Type is `ASTRAVAR_CAMPAIGN_SYNC_WAKE`, version is `1`. Expiry is the earliest of issuedAt+30000 milliseconds, grant expiry, and device credential expiry. No command, gameplay record, source text, or secret is sent through FCM.

The signature is unpadded base64url HMAC-SHA256. Its key is the UTF-8 lowercase hexadecimal SHA256 of the existing device secret. The signed bytes are UTF-8 newline-separated values in this exact order: type, version, campaignId, credentialId, grantId, grantRevision, issuedAt, expiresAt, wakeId. Android must verify every binding, expiry and signature, compare signatures in constant time, reject replayed wake IDs, then fetch typed commands independently through its authenticated client. A wake can never itself authorize or execute a gameplay command.

HIGH FCM priority is used only after the device has reported that it will display its opted-in notification. Devices with denied/disabled notifications register false and receive NORMAL. Delivery remains best effort, may be downgraded, and cannot guarantee sub-second screen-off wakeups.

Set owner-private `ASTRAVAR_SYNC_METRICS=1` to emit request_received/request_completed, queue_accepted, push_requested and push_accepted_by_fcm/push_failed events. Events contain timestamps, random correlation IDs, route category, status and duration; they omit tokens, campaign IDs, character data and source text. Server-Timing exposes request duration only. An FCM acceptance metric proves Google's acceptance, not phone arrival or Room commit. Existing immutable receipts retain the server-recorded receipt time. Device stages and independent saved-revision readback are required before reporting end-to-end latency.

## Lean read selectors

`get_inventory` and `get_equipment` retain their existing unfiltered calls and accept optional `holderProfileId`. `INVENTORY_BY_HOLDER_V1` joins only explicit committed item-placement relations to original items/details/properties, under the same owner/campaign/grant. It never infers assignments from owner display names or invents placements. Missing holder identities return no matches; lack of inventory scope is denied. Migration0006 adds expression indexes for holder, property item and companion resource identity lookups. Tests inspect SQLite query plans to verify both holder and property indexes are used.

`get_character_resources` now returns `RESOURCE_COUNTERS_V1`: only saved resource counters from the selected profile's sheet and its companion counters, with revision, source, freshness and explicit null remaining values. Unrelated capability/spell/research text is omitted. Existing get_character_hp and get_character_abilities remain narrow, scoped selectors. Resource reads use one grant lookup plus one bounded indexed data query; pagination applies each cursor before each branch limit.

All multi-kind reads compare cursor kind and recordId as separate keys. The inherited kind+separator comparison could skip or repeat rows when kinds shared prefixes such as item and item-details; composite comparisons fix that while retaining the existing opaque cursor format.
