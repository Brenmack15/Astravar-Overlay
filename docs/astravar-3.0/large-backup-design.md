# Complete campaign backups above 32 million characters

## Investigation

The code-42 selection bug is an inappropriate caller of `CampaignLedgerRepository.export()`, not evidence of lost campaign rows. `CampaignBackup.snapshot()` reads the typed ledger, histories, reference archive, original source payloads and previous recovery snapshots. `campaignBackupJson` measures the lossless ASCII-escaped JSON before allocating its output. Its independent ceilings are 32,000,000 UTF-16 characters and 32 MiB of bytes. Non-ASCII characters use six-character escapes per UTF-16 code unit; quotes and backslashes in retained JSON sources and nested recovery snapshots expand again. Database size, unescaped source size and serialized backup size are therefore different quantities. No record count or total size of the owner's actual handset is inferred from the error.

Removing the measuring guard or raising one constant is unsafe. The existing document reader, duplicate-key/complexity scanner, typed decoder, preview, conflict validator, recovery snapshot and restore still retain substantial complete collections or Strings. A streaming encoder alone does not provide a bounded-memory, restorable backup.

Code 43 separates character reads from all of these operations. The existing full-JSON backup limits remain enforced, with explicit failure and no claim of a complete backup when they are exceeded. No recovery snapshot, source body, attachment, audit, receipt or campaign row is removed to get below a size threshold.

## Concrete replacement format and write protocol

Use a separate versioned `astravar-campaign-bundle` ZIP64 format, not an incompatible change hidden behind the current JSON schema number. The manifest declares scope, supported versions, required features, database user versions and Room schema identities. It enumerates every included table, column/type/key definition, row count, entry byte length and SHA-256. Include all campaign tables, including prompts and catalog seed/deletion settings that legacy campaign JSON currently omits. The manifest must explicitly identify separate weapon, Reforge, connection and app-preference stores; a campaign-only bundle must never claim to be a complete-device backup. Never export pairing credentials into an unencrypted portable bundle.

1. Pin a consistent SQLite read transaction for each included store; serialize exports per store and declare the snapshot boundary. A future coordinated all-store backup needs a common write barrier across app repositories before claiming atomicity across databases. Concurrent external writers must either honor the same lock or force a new snapshot/review.
2. Page stable primary-key ordered metadata and rows. Use `substr(CAST(text AS BLOB), offset, size)` for large TEXT, with exact byte counts and strict incremental UTF-8 validation, avoiding Android CursorWindow limits. Retain raw original source/recovery strings and binary attachments in individual entries, without JSON-within-JSON expansion. Do not normalize immutable strings, IDs, revisions, timestamps or old receipts. Bound every page, field chunk and encoder buffer; do not materialize `LedgerExport` for the entire database.
3. Write a private staged file with row streams and content entries. Hash bytes as written and record expected lengths and counts. A manifest references each original identity, including duplicate content with distinct identities; optional byte deduplication must retain every original identity and original digest. No reachability pruning or history compaction.
4. Close, reopen and verify the private staging file, then copy to the user-selected document. Close and independently reopen the provider document and verify the entire archive and entry hashes/lengths/counts. Only then mark backup success or permit a recovery-dependent action. Disk full, cancellation, process death, provider truncation and verification failures leave success unset; partial documents must be visibly identified or deleted only when provider cleanup is supported. Always retain source app data.

## Restore protocol

Restore is a separate implementation milestone: a large export without a large restore path is an archival copy, not a verified recoverable backup.

1. Copy into private staging with explicit byte/disk quotas. Validate ZIP paths, duplicates, missing/extra entries, entry count, compression ratio, expanded size, hashes, UTF-8, schema and required features. Enforce budgets during streaming, not only after decompression; reject unknown required features and malformed JSON/duplicate members.
2. Decode into isolated staging tables, preserving original identities, SQL nulls, source bytes and revisions. Validate foreign keys and all original audit/receipt/fingerprint chains. Verify schema-4/schema-5 compatibility without rewriting historical snapshots. Do not run imported triggers or arbitrary SQL.
3. Compute a deterministic source-state fingerprint and compare against a fresh transactional destination read. Show additions/conflicts; user confirmation is mandatory. Conflicting existing records remain rejected. The restoration plan must include all tables in the declared scope; omitted prompts/settings cannot be silently reported restored.
4. After a verified current recovery bundle exists, merge missing rows in a single transaction per store and append a separate immutable restore receipt. Cross-store restores require a journal and recovery protocol before they can advertise all-or-nothing behavior. Idempotent retries cannot change command content. A changed local revision invalidates approval.
5. Independently read back complete counts, identities, revisions and content digests. A repeat restore must be idempotent. Delete private staging only after completion or explicit cleanup; never clear or replace the live database to recover from an error.

## Evidence and acceptance

`CampaignLargeBackupDesignTest` verifies the existing fixed-buffer JSON writer with a synthetic source over 33,000,001 characters, Unicode, escaped quotes/backslashes and an original recovery snapshot. It checks maximum 8 KiB sink writes, independently reopened file SHA-256, exact decoded values and rejection of truncated-byte equality. Host-only decoding is deliberately distinguished from bounded Android restore. The scoped selection regression also proves that this size still fails the old complete export while character preview/adoption succeeds and the complete legacy state hash stays identical.

These tests verify components and the diagnosis; they do **not** establish a shipped ZIP64 implementation, bounded production decoder or end-to-end bundle restore. Before enabling the replacement format, require actual optimized Android tests at 33 MB, 128 MB and larger, Unicode-heavy/nested histories, concurrent writes, low memory/disk, corrupted/tampered/duplicate entries, cancellation/process death at every phase, provider truncation, stale review, conflicts and idempotent retries. Test all claimed store/schema versions and compare every retained row and source byte after restore into a fresh isolated installation. Keep the present JSON guards until that acceptance exists.
