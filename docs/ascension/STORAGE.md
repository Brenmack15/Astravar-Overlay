## Existing transaction path

1. `worker.mjs` requires HTTPS and an independently configured owner. The private Sites gateway establishes the web/MCP identity. Android pairs and supplies its own hashed bearer credential through `core.mjs` and `http.mjs`. A direct public deployment that trusts caller-supplied gateway identity headers is outside the security contract.
2. `mcp.mjs`, `campaign-tools.mjs` and `campaign.mjs` validate operation shape, category permissions, grant revision, expected record revisions, bounded batch size, scoped reads and redaction. The gateway distinguishes the connector from the owner. Several operations require a recent device publication (`FRESHNESS=300_000`) before creating a pending command. The command proposal and notification carry different statuses from its receipt.
3. Android's `CampaignSyncDomain.apply` opens `db.withTransaction`, checks canonical command reuse and preconditions, routes relevant operations through Genesis/Reforge, and stores the parent receipt. The Android publication or receipt updates the Worker mirror. `campaign.mjs` has conflict inspection, matching evidence, safe-rebase previews and linked replacements. Existing `PENDING_DELIVERY` and `PENDING_APPROVAL` represent uncommitted work.
4. `schema.sql` applies mirror changes transactionally and rejects conflicting revisions. Existing issued receipts and verified source relations remain evidence. A later change to the same property, a matching wallet balance or an empty scoped read cannot independently prove an older intended purchase or restoration occurred.

The earlier AV-022 list of ten mutation types describes its own audit revision. The inspected head includes typed native actor/item source plans, equipment/defense edits, form changes, HP, recharge, feature use, native crafting, encounter attacks, spell preparation/casting and rests. Their presence in the mirror command parser establishes a route to Android. Only the tested operation/status and independent result establish execution. The `NOTION` importer sharing one Room transaction, typed damage-defense discriminator compatibility and atomic acquire-and-assign fixes already have specific regression fixtures. Reuse these tests and measure cloud equivalents separately.

## Development architecture decision

Extend the owner-private Worker and its D1-compatible transactional relational model. Use an isolated SQLite database through the repository's D1 adapter during development. Keep the existing Worker, package identity and transport boundary. Use one server-side versioned handler per supported operation from both Android and MCP. The native Kotlin engine remains a source of accepted mechanical behavior for conformance fixtures and local previews. A new authoritative implementation requires differential tests for each supported mechanic; a shared payload shape alone does not establish parity.

| Concern | Design constraint and verification |
| --- | --- |
| Scope and authority | Bind all primary/foreign relations to `(owner, continuity)`. Store current authority mode, epoch and revision. Explicit enrollment selects a synthetic/empty continuity or a later reviewed migration. Fence legacy publication, proposal, pending delivery and decision paths against the same mode/epoch. Demonstrate stale clients cannot write after cutover, including pending work created before the epoch changed. |
| Actors and rules | Stable actor and form IDs, independent form revisions, typed source-backed base values/overrides and conditional effects. Model pools once, attach each action/cast/rest to the real pool. Character, action, item and stat views resolve the same canonical sources. Preserve unknown remaining counts. |
| Holdings and wallets | Canonical definition/version, individual instance/stack, legal owner, custodian, storage placement, accessible state, equipment/attunement and quantity. Express a physical transfer and wallet payment in one event. Exact CP/SP/EP/GP/PP integer balances, bounded arithmetic, aggregate display only. Shared item history links each event to its instance, relevant wallet and source version. Archive/restoration cannot reacquire inaccessible holdings. |
| Mechanics and history | Link each attempt, cast, roll, reaction, rest, construction step and result to a stable transaction and its costs. Represent cursor order, in-world time, source publication, recording and execution separately. Store chronology and discovered lore only within authorized visibility. Genealogy edges preserve the version of each original component and its approved integration outcome. |
| Atomicity and retry | Bind a stable command ID to a canonical fingerprint. Check active credential/grant revision, actor scope and expiration, continuity epoch and expected revisions **inside** the committing SQL transaction. A zero-row guarded update must abort the batch. Write domain state, derived history, changes cursor and immutable outcome together. Return the original receipt for a verified exact retry only after reauthorizing the read. Conflicting absolute proposals can be superseded by independently linked evidence. Event operations require same-event evidence. |
| Approval | Persist the exact proposed payload hash, requesting principal, actor scope/revisions, grant revision, approval requirements and dependencies. Approval and refusal require a separately authenticated owner decision. Recheck authorization, current state and expiration when retiring a proposal or committing the reviewed payload. Return the resulting authoritative receipt and expose the surviving approval queue through both owner surfaces. |
| Client cache | Store versioned snapshots/deltas with an epoch and monotonic cursor. Apply each page transactionally, retain the prior readable snapshot on failure, and rebootstrap after revocation/epoch or incomplete coverage. Track the local refresh separately from a cloud commit. Cache and pending intent can never authorize a live mutation. |
| Media and permanent deletion | Keep private bytes in object storage outside transactional bodies. Associate immutable content digest, size/type, approval and entity revision by a reviewed commit after upload/decoding. Garbage-collect unreferenced objects after verifying reference counts and excluding shared assets. A deleted identity requires a minimal tombstone to prevent resurrection by old caches/imports. Separate immutable receipts and purgeable payloads in the schema from the outset. |
| Recovery | Export authenticated versioned manifests with ordered stable identities, explicit unknowns, referenced media digests, receipts and coverage. Stage and validate with a fresh database, then reconcile and require an owner decision. After cutover, retain subsequent committed events during recovery, validate them in isolation, and fence superseded epochs before opening the sole writer. |

The existing `build-worker.mjs` accepts an explicit dependency-ordered module set and checks that the ordered custom migrations exactly reproduce `schema.sql`. Append a new SQL migration, a chained snapshot, and a journal entry together. Keep historic migration bytes stable. The existing `migration-schema.ts` is an intentionally empty schema for generating custom migration metadata. Its empty snapshot table maps are not evidence that the production database has no tables.

## Hosting and operational limits

D1 fits the existing SQLite/D1 contract and the common single-campaign write pattern. Cross-record comparisons and expected-revision guards must fail inside one D1 batch. All `changes=0` cases that invalidate a precondition require a hard SQL failure, because a valid SQL statement affecting zero rows does not roll back by itself. D1 supports transactional batches. Authoritative independent reads should use the primary or a bookmark at least as recent as the committed revision. The local adapter tests SQL behavior and file persistence; provider-runtime deployments and capacity need separate evidence. [D1 database API](https://developers.cloudflare.com/d1/worker-api/d1-database/)

Managed PostgreSQL is a viable alternative when concurrent writers or volume outgrow this service, with serializable transactions and the corresponding application retry requirements. It would require a new service binding, credential lifecycle, new migration and recovery tooling, and provider-specific hosting costs. The present baseline contains no PostgreSQL deployment to reuse. [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html)

At the time of audit the provider's published free D1 allowance includes 5 million rows read and 100,000 rows written daily, a 500 MB database cap and 7 days of Time Travel. Indexes, duplicate history blobs and snapshot frequency directly affect consumption. On the paid plan, Time Travel retention is 30 days. An engineering checkpoint cannot establish the owner's selected billing plan, available account quotas, actual media usage or restore readiness. Start with no paid provisioning. On an authorized staging copy measure records and media bytes, write amplification, query rows, pagination and restore duration before selecting region/capacity or approving a monthly budget. [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/) · [limits](https://developers.cloudflare.com/d1/platform/limits/) · [Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)

The tracked `hosting.example.json` declares D1 and sets R2 to `null`. A private object binding for verified media, a supported decode/resize implementation, the private gateway configuration, isolated environment, backup retention and provider restore exercise remain production readiness prerequisites. A provider database restore spans the entire database. Review its effect on other continuities, retained post-restore transactions, grants and object versions before an owner-approved recovery. Size image costs using stored GB-months and request counts. Recheck the actual plan and provider pricing before any production commitment. [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/) · [R2 pricing](https://developers.cloudflare.com/r2/pricing/)

## Reproducible evidence

On 2026-11-26, from the inspected head using Node `v24.22.3`, `node --test backend/owner-bridge/*.test.mjs` passed **163 of 163** tests, zero skipped. Coverage includes existing scoped MCP/HTTP, native-command validation, receipt/record readback, matching ordered custom migrations and Worker bundling, SQLite restart, conflict resolution, and optional wake semantics. Native instrumentation references include `CampaignSyncNativeTest.nativeAtomicPurchaseRollbackAndRetryPreserveSinglePhysicalIdentity` and `NotionNativeImportTest.publicContextApplyBackupReimportAndRollbackPreserveIdentity`. That backend command did not run Android instrumentation. Cloud-gate evidence must include phone-independent commits, grant revalidation, duplicate/concurrent operations, denial without leaking private records, snapshot/delta recovery, and actual Android cache readback. The 163-test baseline predates those gates.
