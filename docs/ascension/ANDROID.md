# Android entry points and acceptance

Baseline: PR #41, commit `ae5dfc7622da5d225f97279bcdff837f0b2e893f`, on the code-58 ancestry. The observations below come from source inspection. Existing test names identify relevant regression coverage. No new APK, emulator result or handset acceptance follows from this audit.

## Storage and authority boundary

`MainActivity` launches `AstravarScreen`. The screen waits for `GenesisApplicationStorage` readiness and retains a recovery UI on failure. The application storage singleton gives the campaign ledger, playable repository and Genesis authority repository the same Room handle. A separate weapon store can fail independently. The existing recovery routes must stay usable in that state.

`ReforgeCharacterSheet.change` calls the local repository with an actor revision. The sheet also calls the repositories directly for rolling, transfer and several specialized mechanics. Inventory, relationships and campaign tools write through additional ledger and Genesis entry points. Converting a single editor or HTTP endpoint leaves other write paths. Route commands and queries by selected continuity and authority epoch; keep loading, unknown, stale, approval, committed and verified/readback states distinct. Fence command execution on the server as well as at the client. Older clients cannot enforce a newly introduced client guard.

`MainActivity` polls the campaign connection while started. `CampaignConnectionWorker`, the optional wake path in `CampaignPush` and the legacy HP job also synchronize. Native recovery and currently enrolled device-authoritative continuities need separate paths from an explicitly cut-over continuity. Startup, owner authorization, viewing a cached actor and reconnecting must each be safe before any migration approval. Bind client readback to an authenticated continuity, authority epoch and committed revision. After cutover, a local form edit, rest or wallet action cannot report success from a Room save. Reopening a result or changing a page cannot submit a command.

## Cloud client contract and pre-migration installation

An existing private bridge pairing identifies the HTTPS origin, continuity and Android credential. Pairing alone is insufficient for cloud access. An explicit owner request opens the connected cloud workspace only after an independently scoped, cloud-authoritative server snapshot has been read. There is no creation, promotion or upload operation in this flow. A missing continuity, unknown authority, expired credential, wrong subject or partial first snapshot cannot start a cloud workspace. Persist the local routing decision separately from the legacy campaign store.

The cache must distinguish an absent routing decision from a remembered cloud decision whose credentials or snapshot became unusable. Only the former permits the previous device-authoritative workflow. Revocation, scope substitution, errors and offline restarts cannot silently revert a cloud continuity to a local writer. Keep the previously saved local campaign available for explicit private recovery. An authenticated server-side epoch fence is also required for older app versions.

Cache replacement uses a snapshot bound to service origin, continuity, credential subject, authority epoch, grant revision and grant expiry. Every subsequent page must retain those identifiers and the same campaign revision. Publish a complete replacement atomically after the final page, preserving a still-authorized older snapshot on a network interruption. Remove visible prior data when permission is denied or a different grant invalidates its visibility. Reject delayed older revisions. Show offline data as cached and recheck the expiry. A local cache has no endpoint that accepts edits as committed campaign outcomes.

A native command stores its stable identity, original envelope and revision before sending. A retry reuses those bytes. HTTP acknowledgement, a receipt read and subsequent successful state retrieval are separate observations. The owner approval route is a same-origin, authenticated owner page with anti-forgery protection. A device gameplay grant never authorizes a Verify/Refuse decision on the owner's behalf.

## Connected Android implementation

The application checks the protected cloud-workspace selection before constructing a playable repository screen. Tools → Owner connection → Open existing cloud campaign performs an authenticated read of an already cloud-authoritative continuity. The app never creates a cloud campaign or imports the device records through that control. Installation over an older owner-signed package pauses previously configured automatic device publishing until the owner resumes that connection. The upgrade retains the legacy Room databases, owner grants and existing command journals.

The selected workspace persists a fence for each opened continuity. The legacy full-campaign and HP publication paths check that fence. All four connected destinations use the canonical record cache, read-only server projections and the v3 command service. Reopening a selected continuity without access retains its routing fence. A new valid grant, explicit pairing and a fresh scoped read are required to see content again. Refresh runs when the workspace resumes, on explicit request and periodically while visible. Previously authorized offline reads require the original origin, continuity and device credential, plus unexpired device and campaign grants. Cached media is limited to primary thumbnails and participates in access invalidation.

The connected character screen reads computed statistics from the server. Character selection, quick checks, form preview, resources, spellbook, eligible actions and the Roll Manager operate on the selected actor identity. Attack-only, standalone damage, damage on an existing attempt and composite attacks have distinct contracts. The active Inventory, wallets, item history, project stages and genealogy use party projections. Owner requests open a signed-in review page on the enrolled origin. The native credential can display the action count only with an explicit inbox grant. It never confers the authority of the owner account.

The owner can select local artwork, preview the exact bounded PNG and stage it to the authenticated media endpoint. The app checks the upload digest, target and size before requesting assignment. Owner approval of the candidate and target is recorded by the backend. A successful upload alone never replaces the displayed image. Selected files are decoded at bounded dimensions and resampled for storage. Original external source documents remain outside this workflow.
